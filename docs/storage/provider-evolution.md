# ストレージProviderの変更に備える設計

対象はPR #36、`feat/blomp-storage-phase1`、基準HEAD `80cb48970d6cce24c8710aa7a14d2f48fa815888`。この変更の検証はローカルと隔離環境に限定した。

## 境界と運用

- `server/storage/provider.ts` はProvider型、保存先とキーを含む参照、読み取り、任意の読取署名、追加のMultipart契約を定義する。Multipartを持たないProviderはその契約を実装する必要がない。Blompルートではこの契約を使用し、SDKの署名・変換・照合は既存Blompアダプターで行う。既存Google Drive・R2・ローカル書き出しを変更しない。
- Blompのファイル上限は運用者が確認したバイト値を `BLOMP_MAX_FILE_BYTES` に設定する。未設定・不正値では新規書き込みを保留する。既存のカタログおよびアプリの5 GiB受付上限より大きい設定は切り詰める。容量・アップロード・ダウンロード・検証予算は既存の保存先別DBスナップショットから取得する。陳腐化・残枠不足は保留。Multipart、直接ブラウザ転送、無料条件がすべて確認された場合のみローカル開発の受付を開けられる。本番では引き続き無効。
- 上限を引き下げると該当する新規受付・再開・パート署名・新規のMultipart確定を停止する。完了済みの読み取りは既存の容量スナップショットとダウンロード枠で管理する。受付停止で予約や対象を消さない。APIが明示する期限切れ、認証・権限、アカウント停止、容量不足、レート制限を安全なコードに正規化する。根拠のない403は認証・権限に分類する。ブラウザのネットワーク失敗から失効理由を断定しない。
- 保存済みレコードはprovider、location、object key、owner、job/project、サイズ、SHA-256に結合する。アダプターはlocationを検証し、変更後のアカウントで古いキーを解釈しない。旧保存先を表示・操作するには当該接続設定を復元するか、将来の複数接続画面で個別に選ぶ。資格情報の更新は同一のアカウント・名前空間を確認してから行う。同一バケット識別子の再割り当てに備え、新しい名前空間では非秘密のUUIDv4を `BLOMP_ACCOUNT_BINDING_ID` に設定できる。同一アカウントの鍵更新でもUUIDを維持する。既存接続では未設定のまま旧locationを維持し、後から同じ接続にUUIDを足すと別locationになるため、既存接続へ遡及設定しない。同一バケットの再割り当てはプロバイダーから自動検出できない。
- 接続設定の異常はBlompを利用不可として扱い、独立Node APIの既存ルートの起動を継続する。クライアントに資格情報を送らず、ログへは固定コードだけを出す。障害時にも端末ダウンロードは既存経路から選べる。既存R2・Driveへの自動書き込みや課金、公開、削除は行わない。
- 新Providerを追加する際は、独立アダプターと認可された経路を追加し、読取署名・直接転送・再開・チェックサム・容量報告などを個別に検証する。現在のBlomp専用ルート、名前空間、永続化テーブルの制約は維持する。新Providerの実データを汎用カタログとして扱う段階で、承認付きの追加マイグレーションが必要。

## 移行の実装境界

移行はまだ実装していない。将来実装では、対象ファイル・元と先の接続・見積転送量と料金・公開範囲を提示して明示承認を得る。新しい一意なコピーキーを割り当て、保存先とファイルIDに結合した移行記録にチェックポイントを残す。コピー完了後にストリームでサイズとSHA-256を再検証し、元参照のバージョンが同じ場合だけ参照先を原子的に切り替える。コピーの成否が曖昧な場合は再度コピーせず、対象保存先とチェックポイントを照合する。旧参照の削除は別の承認とし、移行でジョブや端末の復旧データを消さない。

## Blomp単独での初期保存方針

新しい既定のクラウド保存先は入力素材・原本素材・途中素材・チェックポイント・完成成果物の5用途すべてでBlomp。用途と既定Providerの対応は `src/domain/storage/destinations.ts` で管理する。既定変更は新規受付にのみ適用し、既存行は保存済みproviderとlocationを解決する。別Providerが未構成の用途を既定にした場合、Blompの受付は保留する。自動退避は行わない。

`009_blomp_file_roles.sql` は用途の制約を追加的に広げる。既存行・キー・所有者・RLS・ストレージ容量は維持する。開発者ストレージ画面から用途を選んでアップロードし、一覧とダウンロードを使う。チェックポイントはJSONおよび不透明バイナリも選択でき、取り込み用の入力・原本素材として扱わない。保存したバイト列を照合する。アプリの端末チェックポイントの自動アップロードや、クラウド上の任意ファイルからの自動復旧は追加していない。

PR #37の変更パスは静的レンダーのフィクスチャ・テスト、`local-project.ts`、`recovery-store.ts`。今回の差分には含まれない。端末書き出しと復旧は従来どおり。Drimeの実装、認証、接続、移行は行っていない。

### 実ファイル受入前のUI確認

UIにも確認済みファイル上限を表示し、サーバーが上限不明を返した場合や確認済み上限・空き容量を超える場合は、ファイルのハッシュ計算やセッション作成を始めず理由を表示する。既存セッションの再開は従来どおりサーバーで再照合する。APIが無効と回答した場合、一覧APIへ続けてリクエストしない。

Blompの公開フォーラムが言及する 5 GB は一部クライアントの分割単位で、無料アカウントのS3オブジェクト上限として使用しない。公式サイトから案内されたS3設定ガイドは今回403で取得できず、公開資料から当該アカウントの上限値は確定できなかった。実UIの受入には、公式回答によるS3ファイル上限と課金条件、承認済み専用データによるCORS・Multipartの確認、Migration 009を適用した隔離APIとテスト用ログインが必要。本番のBlomp無効化は維持する。
