## 入出力と時刻

既存`POST /render-batches`のFnfSnapshot v1をそのまま使用。既存jobの`attempt/retry_of`は人が要求した試行系列として維持し、workerの自動試行は追加tableの`runs`で管理する。FNFは1080×1920、All Versionsは1920×1080、素材はcontain/letterbox、表示SARを反映して正立させる。元version/hashをowner付きcatalogueとV2 verified media_versionsの両方で照合し、diskへstream保存するとき実バイトsize/hashも再検証する。URLや任意filter/commandは入力にしない。使用範囲に含まれないclipの原本はdownloadしない。

整数microseconds→60fps整数frameはV0/V3の最近傍・half-up。clip連結は累積境界を丸め、出力範囲をそのframe列と交差させる。clipごとの独立丸めを禁止。元PTSのformat originを映像・音声共通に使用。切り出す映像は直前の提示frameも参照し、選択末尾より後の素材frameを混入させず、必要な最終frame保持を行う。入力のrotation/SAR/VFRを処理してCFRへ変換する。padding設定を勝手に追加cutへ適用しない。

H.264/libx264、CRF18、medium、yuv420p、60fps CFR、BT.709 SDR。PQ/HLGはBT.2020/matrix情報が揃った場合にlinear float→gamut変換→Mobius tone-map→BT.709 transfer/matrix/rangeとして処理。不明なHDR metadata/BT.2020 SDRは推測せずINPUT_UNSUPPORTED。HDR表示機器との色基準比較は別途必要。

映像segmentは標準1800frame（30秒）、最大100,000個。各segmentは音声なしでencode/検証。frame境界・snapshot・固定version/hash・render mode・出力仕様・encoder buildをplan hashに含める。完了segmentを非公開object/checkpointへ保存し、再開時にdownloadしたhashと全frame PTS/decodeを照合する。不一致はCHECKPOINT_CORRUPTとして停止し、黙って置換しない。video segmentをstream-copyで結合する。

音声は全pieceを1本のfilter graphで結合してから一度だけAAC320kへencodeする。ノイズ除去・音量正規化・EQ等は使わない。48kHz/stereoへの互換変換、cut、必要な先頭/末尾の欠落区間の無音だけを処理する。各pieceは出力frame数×800 sampleへ合わせる。segmentごとのAAC encode/primingは存在しない。音声がない素材は無音を用意する。

FNFのAAC copyは、単一piece、元の共通origin/audio start=0、無cutの元全長、AAC-LC・48kHz・2ch、元durationと整数frame出力durationが1 sample以内で一致するときに限定する。中間cutや複数clip、rate/layout変換が必要なら一度だけAAC320kへ変換する。copy後も同じpriming/PTS/decode検証を通す。無理なpacket境界cutやcopy失敗後の再encodeを自動で繰り返さない。

## Queue、lease、retry

DBのsingleton `render_slot`行lockで全workerを通じて有効なleaseを1つに制限。90秒lease、15秒heartbeat、単調増加bigint fencing token。job探索→owner scope→対象行lock→再検証でclaimし、同時claim/重複outboxで追加実行を作らない。workerは専用NOLOGIN最小権限group `axfluxo_video_render`へSET LOCAL ROLEする。所有権catalogueや原本へのUPDATE/DELETE権限はない。API roleとは分離する。

claim/heartbeat/各checkpoint・quota・公開transactionでownerとactive membershipを確認。取消はheartbeatで検知して子processを停止し、停止確認後cancelledとする。output確定はslotをlockし、未失効の同token/job/ownerとrunning状態を検証。render_outputsのBEFORE INSERT triggerも同じfenceを要求。古いworkerは実object uploadが遅延完了しても参照を公開できない。DB UNIQUE(owner_id,job_id)が二重公開の最終防壁。

既知の通信/サービス一時障害（408/429/5xx・既知network timeout等）、DB一時障害、処理timeoutだけ初回+2回まで、30秒/120秒+0〜10秒jitter。未知のstorage例外・403/configエラーはSTORAGE_REJECTEDとして保留。OOM/disk/quota/resource不足は保留し、自動retry/増設しない。

lease切れはOOM・host loss・単なるkillを区別できないのでWORKER_LOSTとして**保留**する。未知の死因をtransientと仮定しない。operatorが原因・disk/RAM/cgroup OOM状態を確認し、条件を改善したうえで、監査付き運用で同じjobを再queueできる（このフェーズに権限回避resume APIはない）。同jobならcheckpointを再利用し、runs上限は維持。V1の明示retry API（failed/cancelled/interruptedから新job）と混同しない。専用監視によるcgroup OOM通知・保留解除の運用接続は未実装。Dockerはrestart=no、初期replica 1、無断autoscaleなし。

## 検証と公開

ffprobeで寸法/H.264/yuv420p/SAR/60fps/timebase/SDRを確認し、全frameをstream走査してPTS=frame×1000（1/60000 timebase）、期待frame数、durationを確認。ffmpeg `-xerror -err_detect explode`で映像/音声全体をdecode検証。AAC start/duration、packet PTSの単調性、先頭primingのskip_samples、最終packet padding以内のdecoded sample数も検証。decoded mediaをRAMへ貯めない。

`render-staging/owner/job/uuid.mp4`のsegment/candidateと、`render-outputs/owner/job/uuid.mp4`の最終objectを分離。conditional writeのみ。5GiB超はstreaming multipart（part数からsizeを調整、全量Buffer化なし）。実際のremote bytesをstream hash検証した後だけreadyにする。最終objectも検証済candidateと同じhashであることを確認。

resource version、render_output、render_artifact（object参照＋検証記録）、job succeeded、予算精算、slot解放を同transactionで確定。既存状態名succeededがcompletedを意味する。失敗で原本を変更しない。object候補が残ってもDBの確定参照がなければaccess URLは発行しない。

保存候補・checkpoint・最終objectのすべてをV2 owner quotaへ予約し、remote検証完了後usedへ移す。upload応答消失はHEAD＋実バイトhashで確認する。成否不明の予約は保守的に保持する。終了jobのV1計算予約は一度だけconsumed、heldはreservedを維持。実際に使ったCPUの計測課金ではなく、受付時frame単位の固定予約精算である。GC/自動削除/原本へのCASCADEはない。候補を含む追加保存容量が必要。

## 追加API

すべて既存V1のJWT署名/issuer/audience/expiry/CORSを経由し、毎回membership/ownerを検証。API secret/service keyはserverのみ。raw例外・秘密・snapshot・署名URLをlogに出さない。

| API                            | 契約                                                                                                                                             |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| POST /render-all-versions      | `{document: AllVersionsDocument v1}`、Idempotency-Key必須。全長1jobとmodeを同transactionで作成。同キー別文書409。受付/価格/予算未設定は拒否      |
| GET /render-jobs/:id/progress  | `{jobId,state,runs,completedFrames,totalFrames,errorCode,retryAt}`。frame値は映像checkpoint進捗で、100%でも公開前はrunning。待機/保留/失敗を区別 |
| GET /render-outputs/:id/access | 確定済みowner outputだけ短期限HTTPS URL、hash、size。URL発行後にもmembershipを再確認。候補・他ownerは404                                         |

既存batch/retry/cancel API・応答形式は維持。追加progress APIはポーリング可能であり、SSE/WebSocketは追加しない。V4はfrontendのrunnerや編集文書/既存4DBを変更しない。FNF未送信range/名前の保存経路も追加しない。

主なworker code: STORAGE_TRANSIENT / STORAGE_REJECTED / DATABASE_TRANSIENT / PROCESS_TIMEOUT / WORKER_LOST / DISK_FULL / OUT_OF_MEMORY / RESOURCE_LIMIT / QUOTA_EXCEEDED / DEVELOPER_REVOKED / INPUT_MISSING / INPUT_CORRUPT / INPUT_UNSUPPORTED / CHECKPOINT_CORRUPT / VALIDATION_FAILED / LEASE_LOST / CANCELLED / INTERNAL_ERROR。失敗内容はallowlist codeだけを公開する。

## Migration、起動、rollback

`004_video_render.sql`は追加table/role/policy/triggerのみ。ローカル試験DB以外へ適用していない。001〜003を編集せず、原本/output不変trigger、owner FK RESTRICT、RLS/FORCEと既存API権限を維持する。global slotはownerをまたぐqueue調停専用で、API/PUBLICにアクセス権を与えない。起動時migrationやdown migrationなし。

workerのbuild: `npm run build:render --workspace=axfluxo-video-server`。API用JWT設定とは別に、workerは専用VIDEO_DATABASE_URL、既存CLOUD_R2_*設定、VIDEO_RENDER_DISK（既存のseek可能diskの絶対path）、VIDEO_RENDER_MAX_WORK_BYTES（1GiB以上の明示値）、VIDEO_RENDER_MIN_FREE_BYTES（既定512MiB、下限64MiB）が必要。VIDEO_RENDER_ENABLEDは既定false。root起動拒否。VIDEO_ACCEPTING=falseは新受付/明示retryを停止する。価格設定は既存VIDEO_UNITS_PER_FRAMEを使用。

`infra/video/`に非root Linux DockerとCPU/RAM/PID/readonly/cap制限、既定で外部へ出られないCompose、exact FQDN egress policyのreview用templateを用意。接続先制限は実行基盤で強制する。未設定のComposeからInternetへ抜ける経路はない。事前に認可されたDB/R2だけへ通す設定が必要。秘密はserver専用secret injectorを用い、image/build argに埋め込まない。

rollbackは受付停止→claim停止→既存jobのworker drain（SIGTERM、現在のjobを待ち次のclaimを行わない）。table、job、checkpoint、原本、output、予約、履歴とdiskを保持する。強制終了したjobはlease回収時に保留。古いworker/古いschemaへdowngradeしない。契約、cloud作成、本番migration、main push、merge、deployは行わない。

検証結果と残件は [V4検証記録](v4-verification.md) を参照。
