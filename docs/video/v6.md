## 入口、設定、未送信session

`/developer/fnf-showcase/`。frontendは`NEXT_PUBLIC_FNF_SHOWCASE_ENABLED=true`でbuild時に有効化、既定OFF。新規V6受付はserverの`VIDEO_FNF_ACCEPTING=true`と既存`VIDEO_ACCEPTING=true`の両方が必要。価格/owner予算未設定はV1同様fail closed。V4 render workerの既存設定/role/disk/R2を使用し、新しいcloud資源を作らない。

V2 Libraryから明示選択したverified videoのversion/hashを固定する。初期rangeは元動画の全長、譜面名は空欄。rangeは独立しoverlap可能、追加は現在位置から30秒または末尾まで。末尾そのもので追加したゼロ長rangeは拒否。前後trim、V3 timelineの44px以上のhandle/scroll/pinch、数値時刻/1frame移動、個別譜面名、明示削除を利用できる。全体移動は長さを変えず0〜全長へclampする。同開始microsecondsは作成順で安定ソート。削除しても作成順番号を再割当しない。

V3 VideoPreviewへoptionalなcontrolled range/描画frameを追加した。未指定の従来previewは既存動作のまま。V6 sessionは`FnfSession`のメモリーだけで、source・未送信range・譜面名をIDB/localStorage/cloud projectへ書かない。タブ破棄/再読込で未送信内容が消えることを画面に明記する。新しいeditorは受付batchからsource/range/nameを自動復元しない。batch一覧はID/受付時刻のみで、進捗の明示参照はeditorと分離する。

次回用保存はusernameとtemplateだけ。`axfluxo-developer` v1の既存documents storeのowner専用keyにallowlist projectionを保存し、serverのprivate preferencesへrevision/If-Match付きで保存する。schemaにrange/source/chartNamesフィールドを持たず、serverも未知keyを拒否。local保存とcloud保存/409を区別する。cloud設定を再読込する操作は編集中設定を置換する旨を明記し、競合を勝手に上書きしない。

## Layout / preview / render

1080×1920、60fps CFR、MP4/H.264/libx264 CRF18 medium/yuv420p、AAC。余白の初期背景は黒。上部の`HIGH QUALITY VERSION IS ON YOUTUBE`とその下の@usernameは全編表示し、fadeを加えない。固定Noto Sans JPをserverでPNG化し、同じPNGをpreviewにも重ねる。renderer `axfluxo-fnf-showcase-v6.1`、font SHA-256 `c2f3b4d463500a2ddcd3849cded1fceeb9fd6d1c32e6cbecd568453ba50fc68f`。fontは同梱、runtime downloadなし。配置は見出し中心(540,192)、username中心(540,300)、文字幅最大1000pxへ自動縮小する設計値。参考画像の実測値とは主張しない。

通常素材の固定presetは1920×1080、scale=0.5625、上下crop=0。標準素材は幅1080いっぱいで縦中央。固定scaleを保存して再利用し、元の表示寸法がpresetと異なる場合は警告する。異なる寸法を黙って再scalingしない。「現在寸法で幅いっぱいに合わせる」は明示操作でpreset/scaleを合わせる。上下cropはSAR/90度rotation正立後のsource pixel単位、crop→even pixel scaling→黒canvas中心overlay。画面外にはみ出した部分は切れる。無効crop/ゼロpixelは拒否し、32MPを超える中間映像は資源保留とする。

新規probeはSAR/rotationを考慮した表示寸法も記録する。既存immutable versionを書き換えず、過去のprobeに表示寸法がない場合はraw寸法を示して未検証の警告を出す。workerは実原本をprobeし直して処理する。90度以外の特殊rotationはINPUT_UNSUPPORTEDとして失敗し、原本を保持する。VFRはV4の整数frame/共通presentation timelineで60fpsへ変換する。独立rangeは各1本のMP4になり、音声もrange全体を扱う。

音声copy可否はV4 `canCopyAudio`をそのまま使う。単一sourceの正確な全長、共通origin/audio start=0、AAC-LC/48kHz/stereo、frame/sample duration適合時だけcopy。cut/sync/互換性が不適合なら高品質AACへ1回変換。音量/速度/音声fade/normalizationの操作は追加しない。fallbackのmono→stereo互換変換はV5と同じunity複製、movie timescale=240000で短区間のms丸めを避ける。V4の非template出力条件は維持する。

## 一括受付、filename、snapshot

V0 FnFSnapshot v1は非overlap/strictのまま。新規`kind: fnf-showcase-snapshot`、schemaVersion 1を別定義し、serverの明示discriminator readerだけが扱う。V1の旧`POST /render-batches`でV6形式を受け入れるようにはしない。snapshotには全長source文書、開始順range、元chartNames、安全なnames、creationOrders、実行時preferencesを固定する。未知schema/kind、ゼロframe、source/hash/duration不一致、ソート偽装を拒否する。

filenameは元の譜面名を変更せず別投影とする。NFC、日本語を保持し、path/control/bidi/Windows危険文字、予約名、末尾dot/spaceを処理し、UTF-8/UTF-16長を安全範囲へ収める。同名は大文字小文字を含めて衝突を検出し`name.mp4`、`name (2).mp4`等へ決定的に連番化。生成結果をserverでも再計算して検証する。R2 keyにはfilenameを使わずUUIDを使用するため、別batchを含め既存objectを上書きしない。FNF output accessのContent-Dispositionへsnapshotのfilenameを渡し、日本語名をRFC5987で署名する。旧V4/V5のdownload filename動作は変更しない。

同owner+Idempotency-Keyでsnapshot一致は同じbatch、不一致409。全job/pin/outbox/予約を既存V1の同transactionで作る。各rangeが独立jobとなり、rangeIndexが開始順に対応する。queueの同時刻tieもbatch/rangeIndex順へ決定的にする。実行・checkpoint・lease/fencing・検証後の一意公開はV4のまま。accepted snapshotがserverにあるため、ブラウザーを閉じてもworkerは続く。

通信断などで受付成否が不明なら、メモリー内の同snapshot/同keyを保持して結果を再確認する。その間は編集中内容を変えない。明確な入力拒否では編集を解放する。次のtabでそのdraftを復元せず、受付済batch一覧から明示参照できる。workerはJWT tokenをsnapshotへ保存しない。

retryはV1の既存endpointで失敗rangeだけ新attemptを作り、V6 snapshot readerを使用する。成功jobはretry不可。過去outputのID/hashを変更せず、他rangeを作り直さない。UIは各rangeの最新attempt、frame進捗、状態、個別MP4保存カードを表示。20件ずつ表示でき、ZIPを要求しない。期限切れの保存URLはカードから再取得する。

## API / migration / security

| API                               | 内容                                                         |
| --------------------------------- | ------------------------------------------------------------ |
| GET /preferences/fnf-showcase     | preferences/revision、未設定はdefaultとrevision 0            |
| POST /preferences/fnf-showcase    | strict preferences、If-MatchとIdempotency-Key。別revision409 |
| GET /fnf-showcase/source/:version | ownerのverified source、寸法/全長/固定reference              |
| POST /fnf-showcase/overlay        | preferencesから全編固定の文字PNG、font/renderer metadata     |
| POST /fnf-showcase/batches        | 新規V6 snapshotの原子的受付。各rangeのjobを返す              |
| GET /fnf-showcase/batches         | ownerのaccepted ID/時刻をcursor一覧                          |
| GET /fnf-showcase/batches/:id     | accepted snapshotの各range/name/filenameと既存BatchView      |

すべてV1のJWT署名/issuer/audience/expiry、developer membership、対象ownerを確認し、frontendの表示を認可としない。X-Project-OwnerとJWT ownerの相違も拒否する。overlay生成後にもmembershipを再確認。service role/DB秘密鍵はserverだけ。FFmpegは引数配列・file/pipe whitelist、任意URLなし、秘密/raw例外/signed URL/nameのlogなし。

`006_fnf_preferences.sql`はprivate `developer_preferences`だけを追加するreview用SQL。owner必須、RLS/FORCE、PUBLIC権限なし、APIはSELECT/INSERTとrevision/preferences列UPDATEだけ、DELETEなし。既存table/DB/document schemaへのmigration、down migrationはない。V6 snapshotは既存immutable render_batchesへ保存し、新project tableを作らない。ローカル専用test DB以外に適用しない。

rollbackはfrontend flagをfalseにして再buildし、新規V6受付flagをOFFにする。受付済jobとoutput/checkpoint/原本/preferencesは保持し、既存GET/retry/cancelとworkerは維持可能。DB削除/downgrade、契約、cloud作成、本番migration、main push、merge、deployは行わない。

検証結果と未検証範囲は[V6検証記録](v6-verification.md)を参照。
